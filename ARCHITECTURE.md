# Architecture

Status: 0.8.1 (appearance setting, faster updates, line endings) released on 2026-10-28. CLI phase 1 implemented and verified end to end on one Bilibili video on 2026-10-26 (download, BCut transcription, representative frames, summary context). `summarize`, the Agent skill and the GUI are implemented and tested (2026-10-27); see "Status and open items". Nothing is released until the user says so (user decision, 2026-10-27).

## Platform — user decision

Windows only (user decision, 2026-10-27). Linux and macOS are not supported or tested; CI runs on Windows only.

## Product boundary

The product summarizes local video files regardless of source. Users can select an already-downloaded file directly. An optional `download` command can acquire a video from a supported URL, but downloading ends at a local file path; the user then invokes `process` separately. `process` never downloads implicitly.

## Parts

These parts divide the work by responsibility; additions beyond the user's stated requirements are marked.

1. **Acquisition** accepts an existing local file or, when requested, uses a downloader adapter to create one. The first adapter is yt-dlp. It is optional and separate from processing.
2. **Input and provenance** validates a local video path and records the source path, media facts, selected options, and completed artifacts in a per-video manifest. It never moves or rewrites the source video. **Added:** the manifest makes repeated runs traceable.
3. **Media inspection** discovers audio, video, and subtitle streams and extracts audio needed for recognition. FFmpeg and ffprobe stay behind this boundary.
4. **Transcript acquisition** produces timed text. It checks usable sidecar and embedded subtitles before an ASR provider. Subtitle parsing, correction, search, and export remain independent of a provider. Remote ASR requires an explicit command-line consent flag.
5. **Representative frames** provide visual evidence independently of slide extraction. The sampler combines regular intervals with scene-change candidates, removes exact duplicate images, and records timestamps; since 2026-10-27 it keeps as many as the video has, up to a runaway limit of 500 (see "Layout and screen pages"). Screen pages, one per distinct page of the screen region, come with them on every run. **Added:** it covers silent and visually dense videos; scene changes are candidates, not semantic judgments.
6. **Optional slide extraction** is a separate adapter to AutoSlides Extractor. The CLI invokes its local command-line mode only when the user passes `--extract-slides`; default is off. It writes slide images and a timeline map in a separate output directory. Representative-frame sampling remains independent.
7. **Evidence and summarization** writes `summary-context.md` with timed transcript text and image references. The CLI does not call a language model. The Agent skill `skills/video-agent/` writes `总结.md` from this evidence, adapted from the upstream yanhe-agent skill: the generic template replaces the lecture template, which remains a variant for lecture recordings. `frame` saves extra frames at times the Agent chooses. **Claude judgment:** a skill rather than a model API in the CLI keeps the core free of model-provider dependencies.
8. **Artifacts and jobs** store results in a workspace associated with the selected video. Source videos remain untouched. **Added:** the same artifacts can be consumed by the CLI now and a GUI later.

## Downloader decision — Claude judgment

Use yt-dlp as the optional download backend. Its official project is a command-line downloader with broad site support and documents both stable CLI output (`--print after_move:filepath`) and a Python embedding API. The project can therefore call it as a separate process and receive the final saved path without parsing human-oriented progress text.

Do not use Media Downloader as the backend. Its repository describes it as a Qt/C++ GUI front end whose default engine is yt-dlp; it is useful as a standalone graphical downloader, but it is a second interface rather than the download engine this CLI needs. The new project will keep its own planned GUI over the shared processing modules.

This choice adds one optional `download` subcommand and an external yt-dlp requirement. It does not change `process` input: `process` continues to accept local paths only. The CLI never chains a download into transcription or summarization; the GUI queues processing after a download unless the user unticks 下载完自动处理 (see "Concurrent jobs"). The current Media Downloader-managed executable is auto-detected from the user's AppData directory; Video Agent does not install or update it. Since 0.1.1 yt-dlp is also a Python dependency (see "Distribution"), so `download` works out of the box; a yt-dlp on `PATH` or Media Downloader's copy still comes first.

## Site subtitles and Bilibili login — user decision (2026-10-27)

The user expected a downloaded Bilibili video to come with the platform's subtitles. `download` now saves the site's subtitle tracks beside the video (`--write-subs --sub-langs all,-danmaku,-live_chat`; `--no-subs` turns this off), and `process` takes `clip.<language>.srt`/`.vtt` as well as `clip.srt`, preferring the plain file, then Chinese, then other human tracks, then AI tracks (`ai-*`). Only language-like parts count, so `clip.part2.srt`, which belongs to `clip.part2.mp4`, is not taken. A failed subtitle request makes yt-dlp drop the whole video, so the download is retried once without subtitles. Titles get `_` for `/` and `\` before yt-dlp names the file (user decision, 2026-10-28): Windows forbids both in file names, yt-dlp's own replacements are the maths symbols `⧸` and `⧹`, which read oddly, and the user did not want the fullwidth `／` and `＼` either (half-width `|` is forbidden too). Files downloaded earlier keep their names, since renaming would orphan their processing folders, which are named after the video's path.

Bilibili lists subtitles, AI ones included, only to a logged-in account. `--cookies-from-browser edge` failed on the user's machine with Edge running (locked cookie database), and yt-dlp cannot decrypt the app-bound encrypted cookies of Chromium 127 and later even with the browser closed. The user chose a login inside the GUI: the 设置 dialog and a hint under the download box open Bilibili's login page in a window of the app's own, whose cookies live in a separate persistent partition. The packaged app turns on Electron's `enableCookieEncryption` fuse, so they are stored encrypted with DPAPI; in development (`electron .`) they are not. For each Bilibili download the main process writes the partition's `bilibili.com` cookies to a Netscape file under `<userData>/cookies/`, passes it as `download --cookies`, and deletes it when the job ends and at start. The CLI only accepts `--cookies FILE`; it never reads a browser.

## Collections — user decision (2026-10-28)

The user decided to retire yanhe-agent and move its useful parts: the platform side (finding lectures on Yanhekt, its fast transcripts, downloads) belongs to AutoSlides, and the course organisation to video-agent, generalised so that nothing assumes lectures. A collection is an ordered set of related videos: a course, a series, a playlist, a workshop.

- **Storage** (`src/video_agent/collection.py`): `<workspace>/合集/<name>/collection.json` holds the videos in order, shared terms and skipped videos with reasons; the collection's own files, `合集总结.md` (overview) and `学习提纲.md` (study guide with self-test questions), sit beside it and link each video's `总结.md` as `../../<video folder>/总结.md`. Videos keep their own folders.
- **Commands**: `collection create|add|remove|show|delete|skip|terms|list`. `show` reports each video as processed, summarized, its length, share of speech and `maybe_empty` (under 120 s or under 10 % speech, after yanhe-agent's empty-lecture check); `skip --reason` records why a video is left out. `terms` are corrections shared by the collection: stored with every member (also members not processed yet) beside the video's own, so leaving the collection takes them away; the video's own correction wins on the same form. `download --playlist --collection NAME --workspace WS` fills a collection in order.
- **Writing**: the overview and the study guide are written from the members' summaries, which already link their pictures, so they need no images: `summarize --collection NAME [--guide]` with a model API (refused while a member that is not skipped lacks a summary), `pack --collection` and `summarize --collection --import` for chat AIs, and the skill's "A collection" workflow for Agents, which may hand a few videos to each subagent. The template's overview gained a 需留意 section and column (deadlines, tasks, warnings and notices gathered from the videos, generalised from attendance, assignments and exams) and a skipped-videos section; the study guide covers 重点 (what the speakers stressed, such as exam hints), topics and self-test questions with folded answers and sources.
- **Window**: a 合集 list in the sidebar; a collection page lists the videos with their states (open, skip with a reason, take out), adds videos from the list (a prompt option first, so nothing is added by accident) or from files, queues processing and summaries for the videos that lack them, writes the overview or the study guide by the chosen route (Claude Code, Codex, model API, or copy and import for chat AIs) as queue tasks of their own, one at a time per collection, shows both files with links that open a video's summary, and edits the shared terms; the video page gains 加入合集. Everything goes through the CLI.
- **Lists from a link** (user report, 2026-10-28: a Bilibili season could not be downloaded in one go from the window, which never passed `--playlist`): `download` without `--playlist` still downloads nothing for a link that stands for a list, but with `--json` it prints `{"playlist": {url, title, count, titles}}`; the window then asks whether to download the whole list and, by default, to put it in a collection named after the list (Claude judgment on the flow: asking keeps a pasted season from starting a large download unseen). Bilibili's quick list check gives no entry titles, so the prompt shows only the title and the count.
- **The sidebar** (user decision, 2026-10-28): a video in a collection is listed under the collection, not under 视频; a video taken out of every collection returns to 视频. Since 2026-10-28 (user request: scrolling and switching in the narrow sidebar was awkward) the sidebar lists collections only, with the number of their videos' queued or running tasks; their videos open from the collection page, and a video's page leads back with 「← 合集 · 第 N 集」. Before, a collection spread out its videos under it. The window still keeps the video among its known videos, so its page, tasks and states work as before; 移出列表 is hidden for it. A video matches a collection's entry by the path it was added with or by the CLI's resolved one, since a short 8.3 name (`RUNNER~1` in CI's %TEMP%) comes back long; CI caught this, and a local run with %TEMP% set to a short name reproduces it.
- **Following a list** (user request, 2026-10-28: how to get the new episodes of a series that is still running): a collection may keep its source, the list's link and download folder (`source` in `collection.json`); `downloaded.txt` beside it is yt-dlp's download archive, so `collection update` downloads only videos not fetched before and adds them at the end, and "nothing new" is a normal result. `download --playlist --collection --follow` records the source and fills the archive on the first download; `collection follow NAME URL` adds a source to an existing collection, whose first update finds the files already there and only records them. In the window, the list prompt offers following (on) and checking on its own every six hours while the app runs, also in the tray (off), and the collection page shows the list, the last check and its count, 检查新视频 and the same switch. A check is a download task (the Bilibili login applies; 下载完自动处理 processes the new videos) and does not switch away from the page the user is on. Claude judgment: the automatic check is off unless chosen, since it may start large downloads.
- **yanhe-agent archived** (2026-10-28, at the user's request): its README now says it is discontinued, that the processing and course parts are in video-agent and that the platform part waits for the AutoSlides command line (AutoSlides #35), and the repository is read-only rather than deleted, so the link in that issue still works.
- **Not moved**: slide decks as PDF (AutoSlides exports them) and a separate command for "recent" questions (an Agent answers from the summaries).

## BCut client — user decision (2026-10-28)

The BCut (必剪) client came, through yanhe-agent, from windlandneko/yanhekit's code. Using BCut for subtitles and packaging summaries as an Agent plugin are common ideas (SocialSisterYi/bcut-asr since 2022, VideoCaptioner, BiliNote and others), so the user had the client written anew for this project rather than credit an origin of ideas it did not have (`src/video_agent/providers/bcut.py`, written from the protocol, not from either earlier client). The aim was the best fit, not a restructuring:

- The parts BCut asks for go up four at a time: 37 MB (a 98-minute lecture) took 4.0 and 5.2 s against 11.4 and 11.2 s one part after another (same audio, alternating runs, 2026-10-28).
- The result is polled from 1 s, slowing to every 10 s, so a short clip is done in seconds; progress names the queue, recognition and the line count instead of a line every 10 s.
- The wait follows the audio's length (its full length plus ten minutes; `extract_audio` writes 48 kb/s, so the size gives the length) rather than a fixed two hours.
- Connection failures and 5xx answers are retried quickly; Bilibili's throttling (412 or 429) waits 30, 60, 120 and 240 s, said in the progress. The first draft of the rewrite left 412 to fail at once; the user's question whether the new client was better found it.
- Empty utterances are dropped; `tests/test_bcut.py` runs the whole protocol against a local server (parallel parts, states, failure, deadline, throttling), which the old client never had.
- Checked against BCut itself: a 90-second clip in 5 s (50 lines) and the 98-minute lecture in 8 parts (2707 lines, ending at 01:38:22).

## Summary versions — user request (2026-10-28)

The user asked that summarizing again never replace a summary on its own, and for a note on imported summaries; the mechanism was left to Claude (Claude judgment on the design, `src/video_agent/versions.py`):

- The current text keeps its name (`总结.md`, `合集总结.md`, `学习提纲.md`), which every link, route and collection reads. Every other version is a file beside it, `总结 (2026-10-28 15-30-12).md`, in the same folder so its `frames/…` and `../../` links still resolve; `<name>.versions.json` records each text's time, source (模型 API · model, 网页 AI, Claude Code, 导入) and note.
- A new text becomes current only when there is none, or when asked (`--make-current`, the import dialog's 设为当前总结, off by default); otherwise it is kept as a version and the window says so. Making a version current keeps the one it replaces as a version; only an explicit delete removes a version, never the current text.
- Claude Code and Codex write files themselves, so the skill saves through `summarize --import --source` like every other route, and the window keeps the current text as a version (`versions --keep`, skipped when an identical copy exists) before an Agent runs, so nothing is lost even if an Agent writes `总结.md` directly.
- The summary tab lists the current text and the versions (time, source, note), shows any of them with a banner, and makes one current, notes or deletes it. Collections use the same files and commands; their page shows the current text only for now.

Importing a chat AI's text (user reports, 2026-10-28) also repairs what chat AIs do to it: Gemini wraps relative links in a Google search and ChatGPT puts them under its sandbox, so a link whose search or path holds a file that exists in the folder is put back as the relative path; the 视频 line is replaced by the one this program writes, so 打开视频 works; and since a chat AI cannot run `video-agent fix`, the material asks it to list recurring mishearings under `## 字幕改正`, which the import applies to the cleaned transcript and removes from the summary. An imported summary of the first NJU lecture had 81 such search links; re-imported, it has none.

- **The transcript marks the picture on screen.** summary-context.md groups the transcript lines under a `▶ screen page from HH:MM:SS: <path>` line (or the frame, for a video without screen pages), as yanhe-agent's and yanhekit's `query` start each run with the slide then on screen; the model links what it sees there instead of matching times itself. A context written before is rewritten on the next pack or summary, without processing again.
- **The points missed, once more at the end.** Chat material ends with a short reminder of the rules a chat AI lost over 120,000 characters (notes not retelling, sections in order, the picture of the point, 补充：, the speaker's strength, the code block); the rules themselves stay in the template. Claude judgment on the wording.
- **Pages built up step by step are one page.** Page thinning also merges a page into the next when the next keeps what it showed and adds to it (`media._added`: fewer than 3 % of the first page's content pixels changed, or the first page nearly blank); the group keeps its first time and its last, complete picture. Steps of one slide and a chat growing in a demo had been kept as pages of their own. yanhe-agent and yanhekit leave this to an Agent looking at contact sheets, which a chat AI cannot do.
- **Frames a chat AI asks for.** The material with pictures tells a chat AI to link a missing picture as `补截:HH:MM:SS`; the import takes that frame into frames/extra and points the link at it (also inside a link Gemini wrapped in a search URL). A time outside the video becomes `补截失败:…`.
- **Local subtitles without a click.** Videos added from disk are processed at once when 下载或添加后自动处理 is on, so a same-name subtitle file is read in (`show` reports `subtitles`, where processing would take them from). A local video's audio is not uploaded by default (user decision, 2026-10-28): for videos without subtitles the window asks first, with 用必剪转录 (saying the audio goes to Bilibili), 只处理画面 or 先不处理. `process --subtitles FILE` (GUI: 字幕 → 导入字幕…) takes an SRT or WebVTT file of any name as the transcript.

Images are copied into the video's folder; AutoSlides' `timeline.json` gives their times (the format its Extractor writes, read by the same code), and images without one take the time of the screen page they look like. ## Cleaned transcript — user decision (2026-10-28)

Until 0.3.0 the rules said to correct mishearings "in your head, not in the file". The user asked for a cleaned transcript that replaces the original in use without overwriting it, a practice taken over from yanhe-agent's `fix`.

- `transcript.srt` and `.txt` stay as acquired. `video-agent fix VIDEO --replace WRONG RIGHT` keeps wrong -> right pairs in `corrections.json` and always rebuilds `transcript.clean.srt` and `.txt` from the original and the pairs (`src/video_agent/corrections.py`), so `--remove WRONG` and `--reset` take corrections back without loss; with no pairs left the cleaned files go. The command prints each changed line and names pairs that matched nothing, and holds the video lock.
- Where a cleaned transcript exists it is the one in use: `summary-context.md` is now written from the manifest and the transcript in use (`processor.write_context`), so a fix reaches every summary route without processing the video again; `show` reports it as `transcript` beside `transcript_original` and the pairs; the window's 字幕 tab shows it with a switch to the original and lists, adds and takes back corrections through the CLI. Processing again re-applies the pairs to a newly acquired transcript.
- Only words are replaced, never sentences, so the cleaned transcript is still what was said. A Latin word matches as a whole word (`react` leaves `reaction` alone); Chinese matches as written, so the rules and the skill say to list only forms that are wrong wherever they occur and to correct one-off mistakes in the summary only. Collections will share their terms (planned with collections).

## Layout and screen pages — user decision (2026-10-27)

Lecture uploads often show the camera picture beside or inside the screen recording. On the user's 97-minute example (1280x410, camera left, screen right) whole-frame sampling missed most pages: scene detection found 7 changes, the regular samples were cut to 36 (about one per 3 minutes), and everything was scaled to 960 pixels wide, so the screen half was about 550 pixels. AutoSlides Extractor kept 9 slides: it compares whole frames, so the moving speaker hides page turns, its classifier dropped 13 of about 25 candidates as not slides because they show the room, and its auto-crop (Canny or YOLO, `--ml-autocrop-maybe`) only runs afterwards on `may_be_slide` frames. The user decided that frame counts follow the video with only a runaway limit, and that layout detection and page detection run on every `process`; AutoSlides Extractor stays optional (AGENTS.md).

- **Layout** (`src/video_agent/layout.py`), read during the sampling pass from a 256-pixel-wide grey copy: borders are straight lines present in at least 85 % of 120 sampled frames, either across the frame away from its edge (a split) or closing a box in a corner (a camera inset); a split wins over an inset, since board edges inside a camera picture can close a box with the split line. Of the two sides the camera is the one that changes nearly every second: on the example the camera side changed in 99 % of the seconds and the screen side in 21 %, a lecture with much live coding. A side counts as camera at 50 % or more, and the screen must be under 50 % and at most half the camera's share. Without a border the frame is a screen when under 50 %, otherwise a camera (no pages). The result, with the measured shares, goes into the manifest, and `frames/<run>/layout.jpg` shows it (screen green, camera red). `--screen-region X,Y,W,H` overrides it.
- **Screen pages** (`media.screen_pages`), a second pass over the screen region at the source resolution (an inset is blacked out): one frame per second; FFmpeg's `freezedetect` compares each frame with the first frame of the current page and marks the frame at which the region has stayed within a mean difference of 0.0025 (all colour planes) for 2 s. Measured with `freezedetect` itself: a dark label on 0.8 % of a white slide changes it by 0.003-0.004; on the first 400 s of the example 0.004 gave 10 stable periods, 0.0025 14 and 0.002 17, where the quality jump at keyframes starts to count. Each page records when it appeared and how long it stayed (the `freeze_end` events). (Until 2026-10-28 `mpdecimate` did this; it is GPL-only and the installer now ships an LGPL FFmpeg, see "Bundled FFmpeg".) The pages are then thinned on 128x72 grey copies (`media.merge_similar`), because the user found too many near repeats (2026-10-28): a page within 2.5 % of the pixels of its group's first page joins the group, which keeps its first time and last, fullest picture (bullets appearing, a finished line); the same text scrolled by less than a third of the height, as a whole or in its left or right half (an editor beside a terminal), joins too; a return to one of the last 8 pages (switching windows) is dropped; and a page shown for less than 6 s is dropped unless more than half of it is new (another window or slide), so a terminal printing in bursts or a page being typed leaves one page. On the example this went from 285 stable periods to 94 pages, with every slide kept. The 6 s are then tuned per video, as Opencast tunes its segmenter towards a segment count (user request, 2026-10-28): when the pages exceed 75 an hour (at least 30 allowed for short videos) the time goes up through 10, 15, 25 and 40 s, and below 15 an hour it goes down to 4 and 2 s; the value used is `page_shown_at_least_s` in the manifest's `limits`. Only short pages that are not mostly new respond to it, so a slide that replaces the screen is kept at any value, and the same-page threshold is never raised, since that would merge different slides. Two slides in one template can differ in about 4 %, so the same-page threshold stays below that. The pages go to `frames/<run>/screen/page-NNN-HH-MM-SS.jpg`, the manifest and a "Screen pages" section of `summary-context.md`.
- **Costs.** Two decoding passes, as before (the old periodic and scene passes are now one): on the example about 60 s each, the layout analysis about 1 s, the merging under 1 s.
- **Use of the pages.** `summarize` sends every page within its image budget (default raised from 40 to 60): one per image, or on 2x2 or 3x3 contact sheets (`media.sheets`, 1568 px wide, Anthropic's scaling width) when there are more, with the time and path of each tile in the label; the rest of the budget, at least 8, goes to whole frames. Pages are dropped, evenly and with a message, only when 3x3 sheets do not fit either. `pack --zip` holds every page, up to 40 whole frames and 2x2 sheets in `总图/`, which 提示词.md maps to times and paths for chat AIs that take few images. The skill tells Agents to look at all pages in order. The GUI lists the pages above the whole frames, shows `layout.jpg` on the 处理 tab, and lets the user drag the screen region on it and process again with it.
- **AutoSlides Extractor** (`--extract-slides`) now gets the screen region alone: for a split or inset the region is first encoded as its own video (libx264, CRF 18).
- **Limits.** Pages and representative frames stop at 500 each, spread evenly, and the run reports it; the GUI's frame field is empty (no cap) by default, and the old saved default of 36 is ignored.
- **Prior art (checked 2026-10-28).** Mature tools solve slide changes on a screen-only stream: Opencast's video segmenter (ECL-2.0) runs FFmpeg's scene score on the separately recorded presentation track, drops segments under 60 s and tunes its threshold towards about 30 segments per video; PySceneDetect (BSD-3) detects cuts and takes a crop region only by hand. Lecture-capture systems record the screen as its own track, so cutting it out of a composite is left to small projects; an independent survey of their source (henricos/extract-slides, `docs/research/slide-region-crop.md`, September 2026) found that none crops to an automatically found slide region apart from AutoSlides Extractor's contour detector, and that the best picture-in-picture detector samples pairs of frames 1 s apart across the video, as Video Agent's layout reading does. Projects without a licence (bit-admin/slide-crop and its YOLO model, patrickmineault/vid2slides) may be read for ideas but not copied.
- **Not done: cropping to the slide canvas** inside the screen region (black bars, window frames), as slide-crop and AutoSlides' auto-crop do with contours. The user judged it too rare to be worth it (2026-10-28); if needed, reimplement the contour method, do not copy unlicensed code.
- **Not handled yet.** A layout that changes during the video (for example camera only for the first minutes) is read as a whole, so its border may not reach 85 %; then the frame counts as one region.

## Concurrent jobs — user decision (2026-10-27), modelled on AutoSlides

Until 0.2.0 the window ran one job at a time and refused a second one, even a download while another video was being processed. The user asked for the rules to be worked out from what each job reads and writes, and pointed to AutoSlides (its download queue, `renderer/shared/services/downloadService.ts`, and its serial extraction worker) as a model. Jobs are separate processes, so what they share is files:

| Job | Writes | Reads |
| --- | --- | --- |
| `download` | `<workspace>/下载/<title> [<id>].<ext>` and its subtitles (yt-dlp writes `.part` files first) | the network |
| `process` | in the video's folder: `frames/<run>/` and `slide-extraction/<run>/` (new per run), `transcript.*`, `summary-context.md`, `manifest.json`, temporary `.embedded-subtitle.srt` and `.audio-for-bcut.m4a` | the source video, the previous manifest and transcript |
| `frame` | `frames/extra/frame-HH-MM-SS.jpg` | the source video |
| `summarize`, Agent summaries | `总结.md`, sometimes extra frames | manifest, `summary-context.md`, frames |
| `show`, the window's views | nothing | the files above |

Folders are named after a hash of the video's path, so different videos never share files. The rules that follow:

- **May overlap:** downloads with anything (except the same URL); any jobs on different videos; `frame` with anything.
- **Must not overlap:** `process` and summaries on the same video (fixed temporary names, half-written context read by a summary, two `总结.md` writers); two downloads of the same URL (the same `.part` file); changing the workspace while jobs run (results land where the window no longer looks).
- **May overlap but costs:** several `process` runs share the CPU (FFmpeg uses all of it); several Agent summaries each spend the subscription.

How this is enforced:

- **CLI (all front ends).** `process` and `summarize` hold an OS lock on `<folder>/.lock` (`src/video_agent/files.py`); a second writer gives up after 2 s with a message (Windows can take a moment to release the lock of a killed process), and the lock goes away with the process even when it is killed. `transcript.*`, `summary-context.md`, `manifest.json` and `总结.md` are written to a unique temporary file and renamed, so readers never see half a file; `frame` saves through a unique temporary file and takes no lock, since an Agent calls it while writing a summary. The skill tells the Agent to report the lock message rather than retry.
- **GUI queue (`gui/src/tasks.js`, in the main process).** Like AutoSlides, nothing is refused for being busy: tasks wait in a queue with the states 排队中, 运行中, 完成, 未完成 and 已停止. Each kind has a pool, set in 设置 (defaults: 3 downloads, 1 processing, 2 summaries; AutoSlides runs its extraction serially for the same CPU reason); frame captures have no limit. At most one processing or summary task runs per video; this also covers the Agent routes, which write `总结.md` without the CLI. The same work (same kind and target) is not queued twice while queued or running. Tasks start in the order they were added, and one that has to wait does not hold back later ones. The panel at the bottom lists the tasks, shows any task's output, and stops or retries them; the tray shows running and queued counts. The workspace cannot be changed while tasks are queued or running. The rules are a pure function tested without Electron (`gui/test/tasks.test.js`). **Claude judgment:** the queue lives in the main process rather than the page (AutoSlides keeps it in the page), so it survives a reload and keeps running in the tray; queued tasks are not kept across a restart.
- **下载完自动处理** (on by default since 2026-10-28, user request: subtitles that came with a download should not wait for a manual run; it was off by default as a Claude judgment before; the choice is remembered) queues processing for each saved file with the window's frame settings and BCut setting, without slides. Files the download found already saved are not processed again: `download --json` and `collection update --json` mark each path `new` or not (2026-10-28, after a collection of downloaded videos that started following its list queued all of them again). BCut (user decision, 2026-10-28, replacing consent per run): 没有字幕时用必剪转录 is a remembered choice, on by default, and applies to processing after a download too, since a downloaded video without subtitles otherwise ended its processing with exit status 1 and needed a second run; the checkbox says that the audio goes to Bilibili, so a local video can be kept back. The CLI still uploads only with `--allow-remote-asr`, and the skill still asks before an agent uploads.

## Distribution — user decision (2026-10-27, 0.1.1)

## Compression — user decision (2026-10-28, for 0.9.0)

The user asked to save space by re-encoding videos without visible loss, ruled the old rule "never modify the source video" wrong for this, and decided which videos it applies to: this program's downloads by default, videos added from disk only with the user's agreement, and AutoSlides' Yanhekt recordings not at all from here (suggested to AutoSlides instead, bit-admin/Yanhekt-AutoSlides#41; its own compression scales screen recordings down to 360-540p).

- **Measured** on 5-minute clips at the source resolution against the clip (VMAF, FFmpeg 9.0.1 with libvmaf, Core Ultra 5 125H): a 1080p screen recording (H.264, 835 kbps) came to 33 % with SVT-AV1 preset 8 CRF 40 (VMAF 96.9) and 20 % at 10 frames a second (96.8, 17 s); x265 CRF 26 gave 21 % (96.4) but is GPL; Intel QSV AV1 gave 10-17 % (95.8-96.1) in half the time. A classroom camera recording (H.264, 1.75 Mbps) came to 59 % at CRF 40 (94.7), 43 % at CRF 45 (94.1), 34 % with QSV AV1 (92.8). Bilibili's downloads are already AV1 at about 190 kbps.
- **What `compress` does** (`compress.py`): SVT-AV1 preset 8 CRF 40 at the source resolution; a picture that hardly moves (layout.py's measure, on ten minutes of one grey frame a second) goes to 10 frames a second, a moving one keeps its rate; AAC up to 96 kbps is copied, other audio becomes AAC at 64 kbps; subtitle streams and metadata are kept. Videos already in AV1, HEVC or VP9 are left alone. The new file is written beside the old one, checked (duration within a second, smaller), and then replaces it under the same path, so the processing folder and summaries still belong to it; a comment tag marks it, so a second run does nothing. Hardware encoders were left for later: they need more libraries in the bundled FFmpeg and gave a visibly lower score on camera pictures.
- **In the window**: 设置 → 压缩视频 has 压缩下载的视频 (on: a download is compressed, then processed) and 也压缩从本地添加的视频 (off; it says the original is replaced and not kept). 处理 → 压缩这个视频… asks first for a video that is not one of this program's downloads (outside `<workspace>\下载`) while that setting is off. One compression runs at a time, never beside processing or a summary of the same video; when it fails, the video is still processed, from the original.
- **The bundled FFmpeg** gains SVT-AV1 4.2.0 (BSD 3-Clause Clear with the AOM patent licence), built static in the same script; its source tarball goes onto each release beside FFmpeg's and dav1d's. A pip or uv install uses whatever FFmpeg it finds; without libsvtav1, `compress` says so.

## Bundled FFmpeg — user decision (2026-10-28)

A licence review (2026-10-28) found that the installer shipped imageio-ffmpeg's `ffmpeg.exe`, a gyan.dev "essentials" build configured with `--enable-gpl --enable-version3` and x264 and x265, which makes that file GPLv3, without its licence or its corresponding source; and that the frozen CLI carried no licence texts for Python and its packages. Of three ways out (attach the source of FFmpeg and the twenty-odd libraries of that build to each release; build a small LGPL FFmpeg; stop bundling FFmpeg, against the 0.1.1 decision), the user chose to build an LGPL FFmpeg.

- **Build.** `packaging/ffmpeg/build.sh` builds FFmpeg 9.0.2 with dav1d 1.5.4 (AV1 decoding; BSD 2-Clause) and MSYS2's zlib in MSYS2 UCRT64 with GCC, static, without `--enable-gpl`, autodetected libraries, network, devices or hardware acceleration; both source tarballs are pinned by SHA-256 (dav1d's matched VideoLAN's published sum). Every native decoder, demuxer, muxer and filter stays in. The script fails unless `ffmpeg -L` reports the LGPL and the filters and codecs Video Agent uses are present. Video Agent runs `ffmpeg.exe` and `ffprobe.exe` as separate programs, so static linking inside them is fine; what the LGPL asks is the corresponding source.
- **What changed for that.** The two GPL-only parts Video Agent used were `mpdecimate` (screen pages, now `freezedetect`, see "Layout and screen pages") and x264 (the cropped video for AutoSlides Extractor, now FFmpeg's own MPEG-4 encoder at `-q:v 2`).
- **CI** (`.github/actions/ffmpeg`, used by `test.yml`'s installer job and by `release.yml`): restores the build from the cache, or builds it and saves the cache right after it succeeds, keyed on the build script; the installer job's `ffmpeg-lgpl` artifact feeds the local pre-push smoke test. The cli and gui jobs restore the same build from the cache (choco's full FFmpeg only when nothing is cached yet), so the CLI tests run on the FFmpeg the installer ships; all test videos are made with filter sources and mpeg4, which every build can make. Saving early and not cancelling a cold build follow AutoSlides Extractor's workflow, which builds its FFmpeg through vcpkg. The installer job makes its test video with this build (filter sources and mpeg4, as it has no lavfi and no libx264); the other jobs' choco FFmpeg only makes test videos.
- **Freezing** (`packaging/build_cli.py`): imageio-ffmpeg is left out and `build/ffmpeg/bin` goes into the CLI as `ffmpeg/`; `media.tool` looks on `PATH` first (user decision, 0.1.1), then at that copy, then, for pip and uv installs, at imageio-ffmpeg's. The script then processes and packs a generated clip with `PATH` cut down to `System32`, so a missing filter fails the build, not a user.
- **Source and notices.** Each release carries the FFmpeg and dav1d tarballs and `FFmpeg-BUILD.txt` (versions, checksums, configure line). `packaging/notices.py` writes `THIRD-PARTY-NOTICES.txt` into the CLI folder and the installation folder: FFmpeg, dav1d and zlib, Python (its `LICENSE.txt`, which covers the libraries CPython bundles), every frozen Python package with its own licence files, the PyInstaller bootloader (GPL with the bootloader exception), and the AutoSlides colour palette (Apache 2.0, text in `packaging/licenses/`); Electron, Chromium and the JavaScript packages already carry theirs. pip and uv users get FFmpeg from imageio-ffmpeg on PyPI themselves, which Video Agent does not redistribute.

## Updates — user decision (2026-10-27, 0.2.0)

The user asked for a check-and-update function like other desktop software, chose to keep the installer copy for differential downloads (option A), and asked for both ways around blocked GitHub access: the GitHub API and download mirrors.

- **What happens.** The packaged app checks once about 8 s after start (setting, on by default) and on the 检查更新 button; it never downloads or installs by itself. With a new version the 设置 button shows a dot and the dialog shows the release notes; 下载并更新 downloads with progress, 重启并安装 quits (asking first if jobs are running), installs silently and starts the app again. Where the Agent plugin is installed in Claude Code or Codex, the first start of a new version runs the same steps as the install button, so the plugin follows the app.
- **Library.** electron-updater (electron-builder's updater) does the download, the sha512 check, the differential download against the cached installer and the silent NSIS reinstall. Measured on 2026-10-27: 18.7 MB of the 0.2.0 installer's 159 MB lies in blocks that differ from 0.1.1. Until 0.5.0 every update still downloaded the whole installer (user report, 2026-10-28): the app worked out the changed blocks (8.7 MB of 157 MB from 0.4.0 to 0.5.0) but asked for them as several byte ranges in one request, which github.com and ghfast.top answer with 501 (gh-proxy.com accepts it), and electron-updater then fell back to the full download. The release source now asks for one range per request, as electron-updater's own GitHub provider does; one range per request then made the first differential update, 0.6.0 to 0.6.1, slower than a whole download (user report, 2026-10-28: 8.7 MB in 117 requests took 77 s, the whole 157 MB 28 s), as each request costs about 0.7 s of redirects and round trips; so changed runs less than 1 MB apart are now fetched as one range, the bytes between them included (`gui/src/update-plan.js`, wrapping electron-updater's plan; 6 requests for 12.4 MB on that update, Claude judgment on the gap). Six requests one after another still made 0.7.0 to 0.8.0 take 8.4 s for 12.8 MB, 1.5 MB/s against 5.7 MB/s for a whole download (user report, 2026-10-28), so the ranges are now fetched four at a time and electron-updater's own pass reads them from memory, keeping its copying and sha512 check (measured on GitHub with the same six ranges: 7.0 and 7.9 s one after another, 5.3 and 3.8 s at once). The settings say when the last answered check was, through which source and what it found, kept across restarts, instead of only "up to date" (user request, 2026-10-28); the first update that benefits is the one after the release carrying the fix, since the running version does the download. The update-install test now offers changed blocks and a server that refuses several ranges, as github.com does; before, it offered no changed blocks and accepted several ranges, so it never saw the problem.
- **Sources, tried in order** (`gui/src/updater.js`): github.com (`releases/latest/download/latest.yml`, then the versioned `releases/download/v<version>/` folder, which electron-updater needs to find the old blockmap); the GitHub REST API (assets through `api.github.com`, full downloads only, since asset URLs carry no version); a mirror set in the settings; the built-in mirrors `ghfast.top` and `gh-proxy.com`. Each metadata request times out after 15 s and a download without progress for 60 s moves to the next source, since Electron requests never time out on their own and electron-updater returns a running check instead of starting a new one. `HTTPS_PROXY`/`HTTP_PROXY` are applied to electron-updater's session, which otherwise follows only the system proxy. Both built-in mirrors served the 0.1.1 installer with byte ranges on a direct connection on 2026-10-27 (20 MB: gh-proxy.com about 2.5 MB/s, ghfast.top about 0.4 MB/s; github.com through the proxy about 1.4 MB/s; one measurement), so gh-proxy.com is tried first. The user moved both from the blocklist of their proxy rules to direct for this.
- **Signature (Claude judgment).** The installer is not code-signed, so electron-updater only checks the sha512 in `latest.yml`, and a mirror could serve a different `latest.yml`. The release workflow therefore signs `latest.yml` with an Ed25519 key (repository secret `UPDATE_SIGNING_KEY`; backup in Windows Credential Manager on the maintainer's machine as `video-agent:release-update-signing`), and the app accepts `latest.yml` only when `latest.yml.sig` verifies against the public key in `gui/src/update-signature.js`. This is what makes untrusted mirrors usable; Authenticode signing, once there is a certificate, adds electron-updater's publisher check on top. Losing the private key means users must install the next version by hand.
- **Releases.** A `v<version>` tag runs `.github/workflows/release.yml`: it checks the tag against the versions, builds, signs `latest.yml` with the notes from `docs/releases/v<version>.md`, builds the wheel and creates a draft release with the installer, its blockmap, `latest.yml`, `latest.yml.sig` and the wheel. The draft is published by hand after checking; the app sees only published releases. Users of 0.1.1 and earlier have no updater and install 0.2.0 by hand. The version is 0.2.0 rather than 0.1.2 because the updater is a new feature (Claude judgment, the user agreed).
- **Code signing.** Not done; it needs the maintainer to apply. Azure Artifact Signing accepts individuals only in the USA and Canada (Microsoft Learn, 2026-10-27). SignPath Foundation signs qualifying open-source projects for free (Microsoft Learn); according to third-party summaries, SignPath Foundation, not the project, is shown as the publisher (signpath.org could not be opened from the development machine). Certum sells certificates for open-source developers (seen only in search results). Since 2024 an EV certificate no longer skips SmartScreen's reputation check (Microsoft Learn).
