# Architecture

Status: CLI phase 1 implemented and verified end to end on one Bilibili video on 2026-10-26 (download, BCut transcription, representative frames, summary context). `summarize`, the Agent skill and the GUI are implemented and tested (2026-10-27); see "Status and open items". Nothing is released until the user says so (user decision, 2026-10-27).

## Platform — user decision

Windows only (user decision, 2026-10-27). Linux and macOS are not supported or tested; CI runs on Windows only.

## Product boundary

The product summarizes local video files regardless of source. Users can select an already-downloaded file directly. An optional `download` command can acquire a video from a supported URL, but downloading ends at a local file path; the user then invokes `process` separately. `process` never downloads implicitly.

## Parts

These parts divide the work by responsibility; additions beyond the user's stated requirements are marked.

1. **Acquisition** accepts an existing local file or, when requested, uses a downloader adapter to create one. The first adapter is yt-dlp. It is optional and separate from processing.
2. **Input and provenance** validates a local video path and records the source path, media facts, selected options, and completed artifacts in a per-video manifest. It never moves or rewrites the source video. **Added:** the manifest makes repeated runs traceable.
3. **Media inspection** discovers audio, video, and subtitle streams and extracts audio needed for recognition. FFmpeg and ffprobe stay behind this boundary.
4. **Transcript acquisition** produces timed text. It checks usable sidecar and embedded subtitles before an ASR provider. Subtitle parsing, correction, search, and export remain independent of a provider. Remote ASR requires an explicit command-line consent flag.
5. **Representative frames** provide visual evidence independently of slide extraction. The sampler combines regular intervals with scene-change candidates, removes exact duplicate images, and records timestamps; since 2026-10-27 it keeps as many as the video has, up to a runaway limit of 500 (see "Layout and screen pages"). Screen pages, one per distinct page of the screen region, come with them on every run. **Added:** it covers silent and visually dense videos; scene changes are candidates, not semantic judgments.
6. **Optional slide extraction** is a separate adapter to AutoSlides Extractor. The CLI invokes its local command-line mode only when the user passes `--extract-slides`; default is off. It writes slide images and a timeline map in a separate output directory. Representative-frame sampling remains independent.
7. **Evidence and summarization** writes `summary-context.md` with timed transcript text and image references. The CLI does not call a language model. The Agent skill `skills/video-agent/` writes `总结.md` from this evidence, adapted from the upstream yanhe-agent skill: the generic template replaces the lecture template, which remains a variant for lecture recordings. `frame` saves extra frames at times the Agent chooses. **Claude judgment:** a skill rather than a model API in the CLI keeps the core free of model-provider dependencies.
8. **Artifacts and jobs** store results in a workspace associated with the selected video. Source videos remain untouched. **Added:** the same artifacts can be consumed by the CLI now and a GUI later.

## Downloader decision — Claude judgment

Use yt-dlp as the optional download backend. Its official project is a command-line downloader with broad site support and documents both stable CLI output (`--print after_move:filepath`) and a Python embedding API. The project can therefore call it as a separate process and receive the final saved path without parsing human-oriented progress text.

Do not use Media Downloader as the backend. Its repository describes it as a Qt/C++ GUI front end whose default engine is yt-dlp; it is useful as a standalone graphical downloader, but it is a second interface rather than the download engine this CLI needs. The new project will keep its own planned GUI over the shared processing modules.

This choice adds one optional `download` subcommand and an external yt-dlp requirement. It does not change `process` input: `process` continues to accept local paths only. The CLI never chains a download into transcription or summarization; the GUI can queue processing after a download when the user ticks 下载完自动处理 (off by default; see "Concurrent jobs"). The current Media Downloader-managed executable is auto-detected from the user's AppData directory; Video Agent does not install or update it. Since 0.1.1 yt-dlp is also a Python dependency (see "Distribution"), so `download` works out of the box; a yt-dlp on `PATH` or Media Downloader's copy still comes first.

## Site subtitles and Bilibili login — user decision (2026-10-27)

The user expected a downloaded Bilibili video to come with the platform's subtitles. `download` now saves the site's subtitle tracks beside the video (`--write-subs --sub-langs all,-danmaku,-live_chat`; `--no-subs` turns this off), and `process` takes `clip.<language>.srt`/`.vtt` as well as `clip.srt`, preferring the plain file, then Chinese, then other human tracks, then AI tracks (`ai-*`). Only language-like parts count, so `clip.part2.srt`, which belongs to `clip.part2.mp4`, is not taken. A failed subtitle request makes yt-dlp drop the whole video, so the download is retried once without subtitles.

Bilibili lists subtitles, AI ones included, only to a logged-in account. `--cookies-from-browser edge` failed on the user's machine with Edge running (locked cookie database), and yt-dlp cannot decrypt the app-bound encrypted cookies of Chromium 127 and later even with the browser closed. The user chose a login inside the GUI: the 设置 dialog and a hint under the download box open Bilibili's login page in a window of the app's own, whose cookies live in a separate persistent partition. The packaged app turns on Electron's `enableCookieEncryption` fuse, so they are stored encrypted with DPAPI; in development (`electron .`) they are not. For each Bilibili download the main process writes the partition's `bilibili.com` cookies to a Netscape file under `<userData>/cookies/`, passes it as `download --cookies`, and deletes it when the job ends and at start. The CLI only accepts `--cookies FILE`; it never reads a browser.

## Layout and screen pages — user decision (2026-10-27)

Lecture uploads often show the camera picture beside or inside the screen recording. On the user's 97-minute example (1280x410, camera left, screen right) whole-frame sampling missed most pages: scene detection found 7 changes, the regular samples were cut to 36 (about one per 3 minutes), and everything was scaled to 960 pixels wide, so the screen half was about 550 pixels. AutoSlides Extractor kept 9 slides: it compares whole frames, so the moving speaker hides page turns, its classifier dropped 13 of about 25 candidates as not slides because they show the room, and its auto-crop (Canny or YOLO, `--ml-autocrop-maybe`) only runs afterwards on `may_be_slide` frames. The user decided that frame counts follow the video with only a runaway limit, and that layout detection and page detection run on every `process`; AutoSlides Extractor stays optional (AGENTS.md).

- **Layout** (`src/video_agent/layout.py`), read during the sampling pass from a 256-pixel-wide grey copy: borders are straight lines present in at least 85 % of 120 sampled frames, either across the frame away from its edge (a split) or closing a box in a corner (a camera inset); a split wins over an inset, since board edges inside a camera picture can close a box with the split line. Of the two sides the camera is the one that changes nearly every second: on the example the camera side changed in 99 % of the seconds and the screen side in 21 %, a lecture with much live coding. A side counts as camera at 50 % or more, and the screen must be under 50 % and at most half the camera's share. Without a border the frame is a screen when under 50 %, otherwise a camera (no pages). The result, with the measured shares, goes into the manifest, and `frames/<run>/layout.jpg` shows it (screen green, camera red). `--screen-region X,Y,W,H` overrides it.
- **Screen pages** (`media.screen_pages`), a second pass over the screen region at the source resolution (an inset is blacked out): one frame per second; FFmpeg's `mpdecimate` keeps a frame when more than 2 % of its 8x8 blocks differ from the last kept one (a pointer stays below); a page counts once it stayed unchanged for 2 s (animations, scrolling and transitions settle). Pages whose 160x90 grey copies differ in under 1.5 % of pixels from the first page of their group merge into one, keeping the first time and the last picture (typing, pop-ups). Two slides in one template can differ in about 4 %, so the threshold stays low: on the example 1.5 % kept 167 of 285 stable pages and 5 % would have kept 160. The pages go to `frames/<run>/screen/page-NNN-HH-MM-SS.jpg`, the manifest and a "Screen pages" section of `summary-context.md`.
- **Costs.** Two decoding passes, as before (the old periodic and scene passes are now one): on the example about 60 s each, the layout analysis about 1 s, the merging under 1 s.
- **Use of the pages.** `summarize` sends every page within its image budget (default raised from 40 to 60): one per image, or on 2x2 or 3x3 contact sheets (`media.sheets`, 1568 px wide, Anthropic's scaling width) when there are more, with the time and path of each tile in the label; the rest of the budget, at least 8, goes to whole frames. Pages are dropped, evenly and with a message, only when 3x3 sheets do not fit either. `pack --zip` holds every page, up to 40 whole frames and 2x2 sheets in `总图/`, which 提示词.md maps to times and paths for chat AIs that take few images. The skill tells Agents to look at all pages in order. The GUI lists the pages above the whole frames, shows `layout.jpg` on the 处理 tab, and lets the user drag the screen region on it and process again with it.
- **AutoSlides Extractor** (`--extract-slides`) now gets the screen region alone: for a split or inset the region is first encoded as its own video (libx264, CRF 18).
- **Limits.** Pages and representative frames stop at 500 each, spread evenly, and the run reports it; the GUI's frame field is empty (no cap) by default, and the old saved default of 36 is ignored.
- **Not handled yet.** A layout that changes during the video (for example camera only for the first minutes) is read as a whole, so its border may not reach 85 %; then the frame counts as one region.

## Summary depth — user decision (2026-10-27)

The user found summaries shallow. Besides the missing screen pages, the rules asked for it: the first rule, "Map, don't retell", gave only an overview, main points and a timeline unless the user asked for more (a default taken over from upstream in 0.1.0, not a user decision), `summary-context.md` asked for a "concise" summary, and 详细内容 had one line of guidance. Now 详细内容 is the body: part by part, what a viewer would note down, with a length that follows how much the video says, shortened only on request; pictures are worked in where they add something, without a duty to mention each one. The user asked that the rules name no subject or kind of video (they apply to every video) and not require every screen page.

## Concurrent jobs — user decision (2026-10-27), modelled on AutoSlides

Until 0.2.0 the window ran one job at a time and refused a second one, even a download while another video was being processed. The user asked for the rules to be worked out from what each job reads and writes, and pointed to AutoSlides (its download queue, `renderer/shared/services/downloadService.ts`, and its serial extraction worker) as a model. Jobs are separate processes, so what they share is files:

| Job | Writes | Reads |
| --- | --- | --- |
| `download` | `<workspace>/下载/<title> [<id>].<ext>` and its subtitles (yt-dlp writes `.part` files first) | the network |
| `process` | in the video's folder: `frames/<run>/` and `slide-extraction/<run>/` (new per run), `transcript.*`, `summary-context.md`, `manifest.json`, temporary `.embedded-subtitle.srt` and `.audio-for-bcut.m4a` | the source video, the previous manifest and transcript |
| `frame` | `frames/extra/frame-HH-MM-SS.jpg` | the source video |
| `summarize`, Agent summaries | `总结.md`, sometimes extra frames | manifest, `summary-context.md`, frames |
| `show`, the window's views | nothing | the files above |

Folders are named after a hash of the video's path, so different videos never share files. The rules that follow:

- **May overlap:** downloads with anything (except the same URL); any jobs on different videos; `frame` with anything.
- **Must not overlap:** `process` and summaries on the same video (fixed temporary names, half-written context read by a summary, two `总结.md` writers); two downloads of the same URL (the same `.part` file); changing the workspace while jobs run (results land where the window no longer looks).
- **May overlap but costs:** several `process` runs share the CPU (FFmpeg uses all of it); several Agent summaries each spend the subscription.

How this is enforced:

- **CLI (all front ends).** `process` and `summarize` hold an OS lock on `<folder>/.lock` (`src/video_agent/files.py`); a second writer fails at once with a message, the lock goes away with the process even when it is killed. `transcript.*`, `summary-context.md`, `manifest.json` and `总结.md` are written to a unique temporary file and renamed, so readers never see half a file; `frame` saves through a unique temporary file and takes no lock, since an Agent calls it while writing a summary. The skill tells the Agent to report the lock message rather than retry.
- **GUI queue (`gui/src/tasks.js`, in the main process).** Like AutoSlides, nothing is refused for being busy: tasks wait in a queue with the states 排队中, 运行中, 完成, 未完成 and 已停止. Each kind has a pool, set in 设置 (defaults: 3 downloads, 1 processing, 2 summaries; AutoSlides runs its extraction serially for the same CPU reason); frame captures have no limit. At most one processing or summary task runs per video; this also covers the Agent routes, which write `总结.md` without the CLI. The same work (same kind and target) is not queued twice while queued or running. Tasks start in the order they were added, and one that has to wait does not hold back later ones. The panel at the bottom lists the tasks, shows any task's output, and stops or retries them; the tray shows running and queued counts. The workspace cannot be changed while tasks are queued or running. The rules are a pure function tested without Electron (`gui/test/tasks.test.js`). **Claude judgment:** the queue lives in the main process rather than the page (AutoSlides keeps it in the page), so it survives a reload and keeps running in the tray; queued tasks are not kept across a restart.
- **下载完自动处理** (off by default; the choice is remembered) queues processing for each saved file with the window's frame settings, never with BCut (consent is per run) or slides.

## Interface sequence — user decision

Build the CLI first and write the operating documentation. On 2026-10-27 the user brought the GUI back into scope (it had been deferred on 2026-10-26); see "GUI". The CLI means text commands typed in PowerShell or another terminal; it is the first implementation interface, not a requirement that the project remain command-line-only. A GUI will select local files, show the default-off slide option, report progress, and open results by calling the same processing modules.

The current CLI also serves batch processing and future Agent integration. Do not put media processing logic in the GUI or an Agent skill. Do not add a resident MCP server in this phase.

## GUI — user decision, Claude judgment on technology

Implemented in `gui/` (2026-10-27). The first release ships the CLI, skill and GUI together. Scope the user set on 2026-10-27: the GUI calls the same CLI for all media work and supports every summary route side by side, plus an embedded terminal.

- **Summary routes.** (1) Headless Agent: run Claude Code (`claude -p`) or Codex (`codex exec`) with the `video-agent` skill; uses the user's existing subscription and can take extra frames. (2) Model API: an optional CLI `summarize` command sends the transcript and representative frames to a configured vision-capable model (Anthropic, or any OpenAI-compatible endpoint such as a local Ollama); it takes extra frames through tool calling where the provider and model support it (the model asks for a time, `summarize` runs `frame` and sends the image back, and the model continues), and otherwise works from the pre-sampled frames only. Keys live in Windows Credential Manager, never in plain files. (3) Copy material, for chat AIs on the web: `video-agent pack` prints the prompt (rules, template, the exact start of the 视频 line and `summary-context.md`) for the clipboard, or with `--zip` writes it as `提示词.md` together with the frames (user request, 2026-10-27: without them the frames the evidence mentions are useless to a web AI). The frames keep their paths from the video's folder, so the links the AI writes from the evidence still work once its summary is saved there; `summarize --import FILE|-` saves it as `总结.md` under the same lock and overwrite rule, removing a ```markdown fence. The GUI offers 导出 zip and 导入总结 (paste or file) on this route. All routes use the same rules and template, `src/video_agent/prompts/summary.md` (printed by `video-agent template`), so their output has the same shape. Both `summarize` and the GUI are implemented.
- **Embedded terminal.** A terminal panel with a shell the user picks from those installed: PowerShell 7, Windows PowerShell 5.1, Command Prompt, Git Bash. It opens in the video's workspace folder and can run the CLI or an interactive `claude`/`codex` session.
- **Technology (Claude judgment).** Electron, like the AutoSlides app, with xterm.js and node-pty for the terminal (the combination VS Code uses on Windows through ConPTY). Qt, which AutoSlides Extractor uses, has no maintained terminal widget, so the terminal requirement favours Electron. The GUI starts the CLI as a subprocess; no media or summary logic lives in the front end.


```text
video-agent download <URL>... [download options]
video-agent inspect <local-video-path>
video-agent process <local-video-path>... [--extract-slides]

```

`download` prints the resulting local file paths. `process` is a separate command; it obtains local or explicitly requested remote transcript data, samples representative frames, and writes an evidence bundle. `--extract-slides` opts into AutoSlides Extractor. The source video remains in place.

## Distribution — user decision (2026-10-27, 0.1.1)

The 0.1.0 install asked for uv, FFmpeg and, without saying so, git (`uv tool install git+https://…` fails without it). The user chose to remove these steps:

- **Dependencies.** FFmpeg comes from `imageio-ffmpeg` and yt-dlp from PyPI, both declared in `pyproject.toml`. Tools on `PATH` are preferred. `imageio-ffmpeg` has no ffprobe, so `media.probe` reads the needed facts (streams, codecs, languages, duration) from ffmpeg's banner when ffprobe is missing; a test checks both give the same answer. `download` passes `--ffmpeg-location` so yt-dlp merges streams with the same ffmpeg.
- **No git.** The README, the skill and the GUI's last-resort `uvx` use the wheel attached to the GitHub release instead of a `git+` URL. Installing the Agent plugin from GitHub with `claude`/`codex plugin marketplace add edsfod/video-agent` still needs git (both fail with git hidden from `PATH`, checked 2026-10-27), so the desktop app has buttons that install it from its local copy.
- **Desktop installer bundles everything.** `packaging/build_cli.py` freezes the CLI with PyInstaller (Python, ffmpeg, yt-dlp; about 118 MB) into `resources/cli`; the installer grew from 126 MB to 167 MB and needs no network. A frozen build has no `python -m`, so the bundled yt-dlp runs as `video-agent _yt-dlp`. The GUI uses a CLI set in its settings first, then the bundled one, then `video-agent` on `PATH`; its jobs and terminals see the bundled folder first on `PATH`.
- **PATH and shortcuts.** The installer appends `resources\cli` to the user's `PATH` and the uninstaller removes it (`gui/installer/`). Since 0.2.0 a page after the folder choice says so, with a checkbox that is on by default (SignPath's rule to announce system changes); the choice is kept in `HKCU\Software\Video Agent` for updates and silent installs, and CI checks both ways. Desktop and Start menu shortcuts are electron-builder's defaults. electron-builder also copies the installer (about 160 MB) to `%LOCALAPPDATA%\video-agent-gui-updater`; the updater uses it for differential downloads (see "Updates"), and the uninstaller removes the folder, which electron-builder's own uninstaller leaves behind (0.1.1 left it). **Claude judgment:** appending, not prepending, keeps a CLI the user installed themselves first in terminals. The script edits `HKCU\Environment` through the registry API with `DoNotExpandEnvironmentNames` and keeps the value type, because `[Environment]::GetEnvironmentVariable` returns expanded text and writing it back would turn entries like `%USERPROFILE%\bin` into fixed paths. Checked on 2026-10-27 with silent install and uninstall: `PATH` came back byte-identical and both shortcuts were removed.

## Updates — user decision (2026-10-27, 0.2.0)

The user asked for a check-and-update function like other desktop software, chose to keep the installer copy for differential downloads (option A), and asked for both ways around blocked GitHub access: the GitHub API and download mirrors.

- **What happens.** The packaged app checks once about 8 s after start (setting, on by default) and on the 检查更新 button; it never downloads or installs by itself. With a new version the 设置 button shows a dot and the dialog shows the release notes; 下载并更新 downloads with progress, 重启并安装 quits (asking first if jobs are running), installs silently and starts the app again. Where the Agent plugin is installed in Claude Code or Codex, the first start of a new version runs the same steps as the install button, so the plugin follows the app.
- **Library.** electron-updater (electron-builder's updater) does the download, the sha512 check, the differential download against the cached installer and the silent NSIS reinstall. Measured on 2026-10-27: 18.7 MB of the 0.2.0 installer's 159 MB lies in blocks that differ from 0.1.1.
- **Sources, tried in order** (`gui/src/updater.js`): github.com (`releases/latest/download/latest.yml`, then the versioned `releases/download/v<version>/` folder, which electron-updater needs to find the old blockmap); the GitHub REST API (assets through `api.github.com`, full downloads only, since asset URLs carry no version); a mirror set in the settings; the built-in mirrors `ghfast.top` and `gh-proxy.com`. Each metadata request times out after 15 s and a download without progress for 60 s moves to the next source, since Electron requests never time out on their own and electron-updater returns a running check instead of starting a new one. `HTTPS_PROXY`/`HTTP_PROXY` are applied to electron-updater's session, which otherwise follows only the system proxy. Both built-in mirrors served the 0.1.1 installer with byte ranges on a direct connection on 2026-10-27 (20 MB: gh-proxy.com about 2.5 MB/s, ghfast.top about 0.4 MB/s; github.com through the proxy about 1.4 MB/s; one measurement), so gh-proxy.com is tried first. The user moved both from the blocklist of their proxy rules to direct for this.
- **Signature (Claude judgment).** The installer is not code-signed, so electron-updater only checks the sha512 in `latest.yml`, and a mirror could serve a different `latest.yml`. The release workflow therefore signs `latest.yml` with an Ed25519 key (repository secret `UPDATE_SIGNING_KEY`; backup in Windows Credential Manager on the maintainer's machine as `video-agent:release-update-signing`), and the app accepts `latest.yml` only when `latest.yml.sig` verifies against the public key in `gui/src/update-signature.js`. This is what makes untrusted mirrors usable; Authenticode signing, once there is a certificate, adds electron-updater's publisher check on top. Losing the private key means users must install the next version by hand.
- **Releases.** A `v<version>` tag runs `.github/workflows/release.yml`: it checks the tag against the versions, builds, signs `latest.yml` with the notes from `docs/releases/v<version>.md`, builds the wheel and creates a draft release with the installer, its blockmap, `latest.yml`, `latest.yml.sig` and the wheel. The draft is published by hand after checking; the app sees only published releases. Users of 0.1.1 and earlier have no updater and install 0.2.0 by hand. The version is 0.2.0 rather than 0.1.2 because the updater is a new feature (Claude judgment, the user agreed).
- **Code signing.** Not done; it needs the maintainer to apply. Azure Artifact Signing accepts individuals only in the USA and Canada (Microsoft Learn, 2026-10-27). SignPath Foundation signs qualifying open-source projects for free (Microsoft Learn); according to third-party summaries, SignPath Foundation, not the project, is shown as the publisher (signpath.org could not be opened from the development machine). Certum sells certificates for open-source developers (seen only in search results). Since 2024 an EV certificate no longer skips SmartScreen's reputation check (Microsoft Learn).
