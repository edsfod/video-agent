# ADR-0014: 成稿存成结构化数据，Markdown 由程序从数据生成

## 背景

- 视图由程序用单元的接口组合（[ADR-0013](0013-outlines-instead-of-a-linear-body.md)），程序要能按单元、条目、关系读成稿。
- 成稿是一篇 Markdown 时，模型写 Markdown，程序解析、改写、再拼成 Markdown，桌面程序再从渲染出的 HTML 里找回结构。每一层都有自己的特例：程序删掉模型照抄进正文的提示格式、把单元编号换成标题、在要点行末挂图并在下次保存时去掉；桌面程序按粗体文字找回条目、从行末找回要点的图。
- 读文字的地方要的是 Markdown：合集总结把各视频的总结交给模型，谱系按行比对两版文字，链接和路线读 `总结.md`。

## 决策

1. **分三层**：交换格式（模型每一步交回的文字）、数据（成稿的结构）、视图（提纲、单元组件、导出的文字）。模型的文字只在读进数据时解析一次，读不进来的发回原对话重写；此后程序只改数据。编号、标题、链接、画面路径、时间段都由程序从数据画出。
2. **交换格式是行格式的 Markdown**：每一节、每一行有固定写法，行里带上程序要的字段（条目的父节点和边、单元的归属、单元之间的推进边）。
3. **存储**：每一版的数据存成总结旁边的同名 JSON 文件，以它为准；`总结.md` 由程序从数据生成（时间提纲全部展开），给合集总结、谱系比对、导出和别的工具读（用户定）。手改 `总结.md` 不回到数据里。
4. **编号**：单元是 `U` 加起点（`U004027`）；条目在单元内编号，头是 `S0`；跨单元引用写 `U004027.S3`，不统一改编。模型的文字里提到单元、条目、画面、主线都写编号，程序画成标题和链接。
5. **关系写在子节点上**：除了头，每个条目写一个父节点和边的种类（支撑、反驳、步骤、展开），所以漏写程序看得出。
6. **画面按编号挂到条目上**：写单元的对话在「## 画面」里写「#n 用在 S<k>」，正文不写图片路径；程序把编号换成路径。
7. **没有总结者单元**：单元划分的是带时间的条目（[ADR-0012](0012-flat-units.md)），总结者自己展开的东西没有时间。拓展是放在用得着它的单元里的条目或细节；总结者归纳的主结论放在主线上。
8. **完备由结构保证**：提纲由程序从数据生成，时间提纲含全部单元；主线提纲含全部单元，当且仅当每个单元恰好一个归属；点开单元能显示全部条目，当且仅当每个条目都挂在单元树上。程序查后两条。
9. **显示**：桌面程序从数据画单元组件。别的方式写的总结和以前的版本没有数据，照旧按 Markdown 显示。

## 备选方案

1. **数据嵌在 `总结.md` 末尾的注释里**：版本只有一个文件，但读文字的地方（合集总结、谱系比对）都要先剥掉数据才能用；手改正文照样和数据对不上。
2. **Markdown 本身作为存储格式，编号和关系写在注释里，读的时候解析**：解析又成了每一层的事，手改坏了写法就读不进来；「背景」里的病根换了个地方仍在。
3. **只存数据，不存 `总结.md`**：读 `总结.md` 的地方（合集总结、谱系、链接和路线）都要改成读数据，或每次临时生成。
4. **交换格式用 JSON**：条目是长段中文，夹着代码、公式和引号，写进 JSON 要转义，错一处整段读不进来；行格式读不进来的情况已经有发回重写。
5. **全片统一编号（`P1`、`P2`……）**：一个单元的条目增删，后面所有编号都变，引用要跟着重写；单元内编号加单元编号，改写一个单元只影响它自己。
6. **正文里写画面链接**：模型会写错路径，要程序对着清单改正；正文和「## 画面」两处都挂图时还会对不上。

## 影响

- 版本的保存、覆盖、删除、设为当前和谱系，都要把 `总结.md` 和它的数据当作一对处理（`SUM-04`）；`summarize --import` 要能收数据。
- 和现有实现还不一致的地方：
  - 分阶段统一编号、拼成线性的 Markdown（`staged.numbered`、`staged.assemble`），用 `staged.unnamed` 换掉单元编号，正文写画面路径并用 `staged.unlink_dropped` 处理；
  - 桌面程序从 HTML 里找回结构（`summary.js` 的 `gatherPointPictures`、`showEntry`）；
  - 模板里有总结者的「拓展单元」。
