# 文档规则

> 给谁看：在本仓库写或改文档的人和 AI。回答：每类信息放在哪份文档、按什么规则写、怎么更新。
> 本文是文档规则的唯一来源。文字怎么写、为什么 AI 爱写成过程记录、怎么防，见 [writing.md](writing.md)；代码和提交的约定见 [conventions.md](conventions.md)。

## 一、状态和状态转移

| 类别 | 是什么 | 本仓库里 |
|---|---|---|
| 状态 | 项目现在是什么样 | README、ARCHITECTURE、需求、设计、ADR、参考，以及运行和约定文档 |
| 状态转移 | 项目发生了什么变化 | git 提交；发布说明 `docs/releases/`；发布检查记录 `docs/release-log.md` |

**状态文档只写现在。** 描述过去的文字（「原来是……」「1.4 版时……」）要么已经过时，要么和 git 历史重复，一律不写。

- 完整的变化记录是 git。发布说明是一版给用户带来的变化，从提交整理出来，不必完整；局部改动只写进提交信息。
- 两类文字都可以原地改错，目标不同：状态文档改到和现在一致；发布说明和发布检查记录只改到准确描述那次发布，不因后来情况变了而改写，平时只追加。
- 不设 CHANGELOG.md：发布说明就是本项目的变更记录，发布流程（`.github/workflows/release.yml`、`gui/scripts/sign-update.js`）直接读它。

### 不进 git 的过程材料

- `notes/`：调研笔记、宣传稿、进行中事务的输入。放法见 [conventions.md](conventions.md)「文档」。
- `docs/user-notes/`：用户亲手写的原始材料，原样保存，只追加。

### 不进 git 的理论篇章

- `docs/theory/`：总结方法的理论模型，写成连贯的篇章：概念、定义、辨析、判据、推导和被否决的做法的理由。它是需求、ADR 和设计的推导来源，不公开，所以不进 git。
- 正式文档不链接它，也不靠它才能读懂：结论写进需求、ADR、设计，各自写全。它可以引用正式文档的编号。
- 概念、判据或推导变了，先改它，再改正式文档里的结论。

`notes/` 和 `docs/user-notes/` 既不是现在的状态，也不是已发生的变化：想法是还没发生的变化，排查记录是证据。正式文档不链接它们；其中能长期成立的结论，提炼进正式文档再引用（第七节）。

## 二、状态的三个层面

| 层面 | 回答 | 文档 |
|---|---|---|
| 意图 | 系统应该表现成什么样 | [requirements.md](requirements.md)、[summary-requirements.md](summary-requirements.md) |
| 决策 | 在几个方案里选了哪个、为什么 | [adr/](adr/) |
| 实现 | 系统实际怎么做到 | [ARCHITECTURE.md](../ARCHITECTURE.md)、[design.md](design.md) 和各篇 `*-design.md`、代码 |

### 已定未实现、待定

- **已定、还没实现**：意图写进需求，跨模块的取舍写成 ADR；设计文档只写已经实现的。需求里还没实现的部分，「验收」写「未实现」。ADR 的决策和现有实现不一致时，在「影响」里写明哪里还不一致，实现以后删掉这一条；被新决策推翻的旧 ADR 原地改写。
- **待定**：还没定的问题写进它所属的需求或设计文档末尾的「待定」一节，写明要定什么、几种做法各自的代价；定了就写成正文，删掉这一条。不放进 development.md 的「已知问题」：那里只放测试、构建、发布上的问题。

外部系统的客观行为（DeepSeek 网页版、agy）不是本项目的状态，放 [reference/](reference/)，每条注明来源（实测带日期、官方文档、报道），还没查明的列在「尚未查明」。还没排期的方向放 [roadmap.md](roadmap.md)，它不是承诺；决定要做时写成需求。

### 意图是一条链

目标（`G`）→ 场景（`S`）→ 需求（`SRC`、`FRM`、`SUM`、`MGT`、`APP`、`INS`、`PRV`）→ 规格和验收 → 设计。

- 每条需求写「服务于」哪个目标或场景；不显然的取舍写成 ADR 并引用。
- 总结提示词的逐条要求（`PRM-`）都服务于 `SUM-01`，每条写明落在模板的哪一节或程序的哪里。

### ADR

- 一份 ADR 写「从零到现在」的选择：在所有方案里现在选了哪个、为什么。不写「从上一版改成这一版」，那是 git 和发布说明的事。
- 只收跨模块的取舍。只影响一篇设计的决定写在那篇里，写成陈述句加理由。
- 决策被推翻时原地改写这份 ADR，不另写一份去取代它。**被推翻的方案和失败的依据写进「备选方案」**：这是现在的 why，丢了会有人再提一次。
- 仓库里的 ADR 都是当前有效的，不写状态和日期。还在提议中的放 `notes/`；不再适用的（例如相关功能已删除）直接删掉。
- 「不做某事」也是决策，照常保留。
- 标题写现在的决策，不写转移。
- 备选方案的否决理由要有依据：实测、文档、明确的推理。找不到依据的方案不列，不事后补一个看似合理的理由。

## 三、why 写在哪

| 哪种 why | 写在哪 |
|---|---|
| 项目为什么存在 | README 第一段、requirements.md 的「目标」，两处说法一致 |
| 某条需求为什么存在 | 它服务的目标或场景；不显然的取舍写成 ADR 并引用 |
| 为什么选方案 A 不选 B | ADR；只影响一篇的，写在那篇里 |
| 这段代码为什么这样写 | 代码注释 |
| 这次改动为什么这样改、谁哪天定的 | 提交信息 |
| 讨论经过、推理过程 | 对话、`notes/`，不进仓库 |

用户做的决定，在文档里那句话后面标「（用户定）」。「谁有权改这句话」是这句话现在的属性：改之前要先问用户，读的人改的时候就要看到，所以跟着那句话写在文档里；它不是历史。决定的日期和经过是历史，写进提交信息，写成「（用户 YYYY-MM-DD 定）」。代码注释不标，指向文档的那一节。AI 的理解还没经用户确认的，标「（AI 理解，待确认）」，确认后改成「（用户定）」或去掉。不标的是技术判断，明显错了可以直接改。证据的日期照写，例如「实测 2026-10-27」：它说明证据是什么时候测得的，不是谁哪天定的。

## 四、按变化速度分层

| 层 | 多久变一次 | 内容 |
|---|---|---|
| L0 | 几乎不变 | 目标、范围和不做什么；reference/ |
| L1 | 跨大版本才变 | 场景、需求的形态、不变量、ADR、受 ADR 保护的数值 |
| L2 | 增删功能时变 | 代码地图、机制、接口契约、磁盘上的文件 |
| L3 | 经常变 | 代码、测试、可以随手调的数值 |

每份文档只放同一速度的内容，免得改一层牵连另一层。同一类东西也可能分属不同层：受 ADR 保护的数值（例如压缩的 CRF 40）改它要重新论证；只是偏好的数值写在代码里，文档引用常量名。

## 五、一个事实只写一处

- 数值、字段表、命令清单在一个地方写全，别处只引用。
- 代码里有权威定义的，文档写「定义见 X」，不抄字段和数值：`--json` 的形状见 `contract.py`；版本号只用 `scripts/bump_version.py` 改；视频文件夹里的文件名见 `evidence.SUMMARY_NAME` 等常量。一定要在文档里展开的，用测试保证两边一致（例如 `tests/test_names.py`、`test_versions_match`）。
- 下层引用上层：设计引用需求编号，需求不引用类名和文件名。
- 引用稳定的标识：需求编号、ADR 编号、不变量编号（`A1`、`C1`）、文件名、类型名。引用别篇的某一节写节名，不写「第四节」：节号随文档调整而失效。代码注释引用文档时也一样。
- 文档里点名的类型、函数、命令、测试必须真实存在，名字要准确：文件名不等于类型名。

## 六、读者

每份文档只为一类读者写，别的读者给链接。每篇开头两行：给谁看、回答什么；回答不了这个问题的内容不属于这一篇。

| 文档 | 读者 | 回答 |
|---|---|---|
| README.md | 用户，第一次到达仓库的人 | 这是什么、怎么装、怎么用、怎么升级和卸载、出问题怎么办、更多文档在哪 |
| cli.md、commands.md、PRIVACY.md | 用户 | 命令行怎么用、每个命令和选项、隐私和使用须知 |
| ARCHITECTURE.md | 要改代码的人 | 代码在哪、什么不能破坏、改一处要连带改哪里 |
| 需求、设计、ADR、参考 | 要改代码或判断行为对不对的人 | 见第二节 |
| development.md、conventions.md、writing.md、本文 | 在本仓库工作的人和 AI | 怎么测试、构建、发布；怎么写代码、提交和文字 |

README 只写用户需要的：精确的规格链接到需求，机制链接到设计，不写测试和构建的步骤。

## 七、公开范围

仓库是公开的。

- `notes/` 和 `docs/user-notes/` 不进 git。
- 进 git 的文件不写本机路径、用户名、作息和与项目无关的软件使用记录。
- `notes/` 里能长期成立的事实，去掉个人信息后提炼进 reference/、设计或 ADR，再引用。
- 把已进 git 的文件移出仓库时，`.gitignore` 不够：它对已跟踪的文件不起作用，要同时 `git rm --cached`。已推送的历史仍然可见，要不要改写历史另行决定。

## 八、写作规则

适用于所有进 git 的状态文档：

1. **只写现在**：不出现「原来」「曾经」「改为」「新增」「不再」「从 X 换成 Y」「自 1.4 起」「暂时」「目前」这类转移措辞。被推翻的方案有教训价值的，写进 ADR 的「备选方案」。描述程序运行时做什么（「把链接换成……」「这个文件不再处理」）不算转移措辞。
2. **可判定**：每句话都能判断真假，不用「尽量」「适当」「较快」这类无法验收的词。
3. **不写会随代码变化的计数**，如「共 N 项」「N 个测试全部通过」。
4. **编号只增不改，废弃不复用**：需求、`PRM-`、ADR、不变量的编号会被代码注释和发布说明引用。废弃的编号列在所属文件末尾的「已废弃编号」，写明去向。
5. **一句话只说一件事**：需求、验收条件逐条列，不在一格里塞几个条件。
6. **验收条件指向真实可观察的东西**：测试名、命令的输出；写之前确认它确实是这样。只能在实机上看的写「实机：」加步骤。测试和实机判定不了的（例如总结写得好不好），写「人工评审：」加评审办法；办法还没定的，写「人工评审：办法待定」，并列进所属文档的「待定」。格式检查通过不等于满足了这类需求，不能拿来代替。

更多写法和写的步骤见 [writing.md](writing.md)。

## 九、检查

能自动检查的不靠自觉：

- `scripts/lint_writing.py`：过程记录、归给用户的引语、带钟点的记录（[writing.md](writing.md)「从机制上防住」）。
- `scripts/verify_doc_references.py`：代码和文档里出现的需求、`PRM-`、ADR、不变量编号都要存在，废弃的编号只出现在所属文件里；Markdown 相对链接和写出的 `docs/` 路径指向的文件都要存在。`pre-push` 和 GitHub 上每次推送都跑。
- 一个事实只写一处：代码里有权威定义、文档或界面又要展示的，用测试保证两边一致，或改为运行时取值。

不做需求追踪矩阵：在本项目的规模下，它多半只保证编号对齐，维护成本远高于收益。
