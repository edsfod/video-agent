# 开发约定

> 给谁看：在本仓库工作的人和 AI。回答：文档、代码、提交怎么做。必须遵守的硬要求在 `.claude/rules/hard-requirements.md`（每次会话自动加载）；测试、构建和发布的做法在 [development.md](development.md)。

## 文档

- 文档地图和体系见 [README](README.md)。规格（需求、设计、参考、运行、约定）原地改写，只保留当前版本；过程留在 git 历史和对话里。
- 一条事实只有一个归宿：写全在一篇里，别处引用。决定写在它所属的那篇里，带日期；推翻时直接改，不留旧说法，不另设决策日志和交接文档。
- 怎么写见 [writing.md](writing.md)。
- 改动的文档和改动放在同一个提交里。
- 现状以代码为准：文档和代码冲突时先查代码。
- 用户亲手写的原始材料放 `docs/user-notes/`（不进 git，仓库是公开的），文件名英文、带日期 `主题-YYYY-MM-DD.md`，配图放 `docs/user-notes/images/<笔记名>/`；只追加，不改写用户的文字。
- 调研笔记、宣传稿等不发布的材料放 `notes/`（不进 git）。
- `docs/archive/2026-11-20/` 是重构前的文档，冻结，不修改；只当查漏的材料，内容并入新文档后可以删。

## 代码

- 代码照周围代码的样子写：注释密度、命名、惯用法。
- 用 Python 写文本文件时传 `newline='\n'`；`.gitattributes` 让仓库统一用 LF。
- 每个耗时的运行都设时限，输出直接写进文件，跑的过程中读那个文件；不经 `grep`、`tail` 过滤，也不靠完成通知判断结束（卡住的进程不会发通知）。
- `gh` 的监视用 `gh --jq`，不用单独的 `jq`。
- 网页上有什么，用脚本查（DOM、数据、请求），不看截图。
- 改了措辞，到测试里搜旧的写法。
- 发布出去的文件（代码、文档、发布说明）里不写本机的路径和用户名。
- 给模型的提示词里，例子用占位符，不用真实视频的内容：模型会把例子当成视频本身的内容。

## 提交

- 直接推 `main`：提交只带本次改的路径（`git commit -m "…" -- <路径…>`，新文件先 `git add`），然后 `git pull --rebase`，再推。`pre-push` 钩子跑这次改动涉及的快速检查（见 [development.md](development.md)）；不等 GitHub 的运行结果，它发现的问题接着修。发布前例外：要等。
- 提交信息说改了什么；正文写要点和整理后的决定，带日期。

## 给人看的文字

- 平白、直接的中文，不用客套话和翻译腔；结论的强度和依据相当。
- 以用户名义发给别人的文字，先给用户看。发布说明不用先给用户看，要有一节代码改动。
