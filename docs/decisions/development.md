# Development, tests and CI — user decisions and requests (2026-10-27 to 2026-10-29)

How the project is built and tested, and how work reaches `main`. The rules themselves are in `AGENTS.md`.

- Tests: 33 pytest tests, including one that keeps the version equal across `pyproject.toml`, the plugin manifests, `gui/package.json`, the skill and the README; GUI end-to-end tests (`gui/test/e2e.test.js`, Playwright) run from source; against the unpacked build, which CI builds in the `installer` job, only those that reach what packaging changes run again, with the update tests (user request, 2026-10-29: the whole suite ran twice); the rest are declared with `devTest`. After each test, open dialogs are closed and stubbed file dialogs restored, so one failure does not fail the tests after it. `gui/test/agents.test.js` runs the real agent routes only with `VA_E2E_AGENTS`. With `VA_E2E_BACKGROUND` (the tests set it) the window opens off the screen without a taskbar button or the focus, so the tests can run while the user works (user request, 2026-10-29).
- CI hygiene (user request, 2026-10-28, after two red runs on `main` from a smoke test that had only ever run in CI): the local pre-push hook now also freezes the CLI and runs its smoke test when packaging-related files change; `test.yml` cancels a superseded run on the same branch; work goes to a branch and `main` is fast-forwarded only after CI passes there (AGENTS.md). Faster runs (user request, 2026-10-28; Claude judgment on the means): the pre-push hook skips its checks when every pushed commit is already on a remote branch, so fast-forwarding `main` after CI does not repeat them; `test.yml` caches npm packages and the Electron and electron-builder downloads, and the installer job, which sets the length of a run, takes FFmpeg from the cache itself instead of waiting for a separate job and installing choco's. Every CI job has a time limit (2026-10-28, after the update-install test hung two runs for over 20 minutes: taskkill failed on a child of the restarted app that was already exiting, the test threw before closing its update server, and the server kept Node alive); the test now ignores taskkill's exit code and closes its server in any case. A release tag is pushed together with the release branch, so the draft builds while CI runs; it is published only after CI passed and `main` was fast-forwarded (Claude judgment, after the user found releases slow). Tags no longer run `test.yml`. Jobs run by what a push changed (`.github/scripts/changed-jobs.sh`, user question 2026-10-28 why every push ran everything; Claude judgment on the rules): the parts are separate modules, but the window drives the real CLI by design and the installer bundles CLI, window and skill, so CLI or skill changes still run all three jobs, window changes run gui and installer, packaging runs installer, documentation runs none, and an unknown file runs all; the local pre-push hook picks its checks with the same script. The two installer tests print timestamped progress, so a hanging step shows where it hangs while it runs. A push to `main` (a fast-forward to a commit that passed on its branch) repeats no job, except to fill the caches branches read when `gui/package-lock.json` or the FFmpeg build script changed. The release job takes FFmpeg from the cache itself rather than waiting for a separate job. Reusing the CI-built installer for the release was considered and left out: the release now builds in parallel with branch CI, so waiting for CI's installer would make it slower, and building from the tag keeps the release's own record of what went in.
- **Shorter CI** (user request, 2026-10-29: every change waited about five minutes, and a release ten). The installer job, the slowest (build, PATH choice, silent install, update install: about 5 minutes), runs only for changes to dependencies, packaging, the installer, the icons or the updater; window code runs the gui job alone (about 2.5 minutes) and CLI code cli and gui. The release workflow runs the packaged app's smoke tests (about 30 seconds) before it creates the draft, so a change that broke only the packaged app still stops a release. A commit that only changes the version (`.github/scripts/version_only.py`, which also accepts README.md's wheel link left on the last full release during a pre-release) runs only the cli job's version check, and the local pre-push check skips packaging for it.
- Working on `main` (user decision, 2026-10-29, as waiting on GitHub made every change slow): the tests a change touches run on this machine before a push (the pre-push hook, GUI windows off the screen), then it goes straight to `main`; GitHub's runs follow without being waited for; installer tests run only on GitHub and only for packaging changes. This replaces the branch-then-fast-forward rule above.
- README (Chinese) with screenshots in `docs/images/`, made by `npm run screenshots` from NASA's public-domain video GSFC_20181108_FERMI_m13042_Luck4K and its official captions (both fetched from images.nasa.gov), with an AI-output disclaimer as NASA's media guidelines ask.
