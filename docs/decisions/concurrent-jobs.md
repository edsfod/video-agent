# Concurrent jobs — user decision (2026-10-27), modelled on AutoSlides

Until 0.2.0 the window ran one job at a time and refused a second one, even a download while another video was being processed. The user asked for the rules to be worked out from what each job reads and writes, and pointed to AutoSlides (its download queue, `renderer/shared/services/downloadService.ts`, and its serial extraction worker) as a model. Jobs are separate processes, so what they share is files:

| Job | Writes | Reads |
| --- | --- | --- |
| `download` | `<workspace>/下载/<title> [<id>].<ext>` and its subtitles (yt-dlp writes `.part` files first) | the network |
| `process` | in the video's folder: `frames/<run>/` and `slide-extraction/<run>/` (new per run), `transcript.*`, `summary-context.md`, `manifest.json`, temporary `.embedded-subtitle.srt` and `.audio-for-bcut.m4a` | the source video, the previous manifest and transcript |
| `frame` | `frames/extra/frame-HH-MM-SS.jpg` | the source video |
| `summarize`, Agent summaries | `总结.md`, sometimes extra frames | manifest, `summary-context.md`, frames |
| `show`, the window's views | nothing | the files above |

Folders are named after a hash of the video's path, so different videos never share files. The rules that follow:

- **May overlap:** downloads with anything (except the same URL); any jobs on different videos; `frame` with anything.
- **Must not overlap:** `process` and summaries on the same video (fixed temporary names, half-written context read by a summary, two `总结.md` writers); two downloads of the same URL (the same `.part` file); changing the workspace while jobs run (results land where the window no longer looks).
- **May overlap but costs:** several `process` runs share the CPU (FFmpeg uses all of it); several Agent summaries each spend the subscription.

How this is enforced:

- **CLI (all front ends).** `process` and `summarize` hold an OS lock on `<folder>/.lock` (`src/video_agent/files.py`); a second writer gives up after 2 s with a message (Windows can take a moment to release the lock of a killed process), and the lock goes away with the process even when it is killed. `transcript.*`, `summary-context.md`, `manifest.json` and `总结.md` are written to a unique temporary file and renamed, so readers never see half a file; `frame` saves through a unique temporary file and takes no lock, since an Agent calls it while writing a summary. The skill tells the Agent to report the lock message rather than retry.
- **GUI queue (`gui/src/tasks.js`, in the main process).** Like AutoSlides, nothing is refused for being busy: tasks wait in a queue with the states 排队中, 运行中, 完成, 未完成 and 已停止. Each kind has a pool, set in 设置 (defaults: 3 downloads, 1 processing, 2 summaries, 1 compression, the last settable since a user request on 2026-10-29; AutoSlides runs its extraction serially for the same CPU reason); frame captures have no limit. Summaries through DeepSeek's web chat count as summaries, each in a window of its own (user request, 2026-10-30; one at a time before). At most one processing or summary task runs per video; this also covers the Agent routes, which write `总结.md` without the CLI. The same work (same kind and target) is not queued twice while queued or running. Tasks start in the order they were added, and one that has to wait does not hold back later ones. The panel at the bottom lists the tasks, shows any task's output, and stops or retries them; queued and running tasks have a tick box, and 停止所选 stops the ticked ones, 全部停止 (after asking) all of them (user request, 2026-10-29, while compressing a batch); the tray shows running and queued counts. The workspace cannot be changed while tasks are queued or running. The rules are a pure function tested without Electron (`gui/test/tasks.test.js`). **Claude judgment:** the queue lives in the main process rather than the page (AutoSlides keeps it in the page), so it survives a reload and keeps running in the tray; queued tasks are not kept across a restart.
- **下载完自动处理** (on by default since 2026-10-28, user request: subtitles that came with a download should not wait for a manual run; it was off by default as a Claude judgment before; the choice is remembered) queues processing for each saved file with the window's frame settings and BCut setting, without slides. Files the download found already saved are not processed again: `download --json` and `collection update --json` mark each path `new` or not (2026-10-28, after a collection of downloaded videos that started following its list queued all of them again). BCut (user decision, 2026-10-28, replacing consent per run): 没有字幕时用必剪转录 is a remembered choice, on by default, and applies to processing after a download too, since a downloaded video without subtitles otherwise ended its processing with exit status 1 and needed a second run; the checkbox says that the audio goes to Bilibili, so a local video can be kept back. The CLI still uploads only with `--allow-remote-asr`, and the skill still asks before an agent uploads.
