# DeepSeek 网页版

> 给谁看：要改 DeepSeek 网页路线（`gui/src/deepseek.js`、`chat-rounds.js`）的人和 AI。回答：chat.deepseek.com 的页面实际怎么表现、怎样用脚本查它。
> 证据级别：「实测」带日期，是用户的账号、脚本读页面和请求得到的；「报道」是第三方的说法，没有官方数字。页面会变，拿它做决定前先用脚本再查一次。

## 能力

- 看得懂图片，不只是读图里的字：读得出柱状图最高的是哪一根、有几个峰（实测 2026-10-29）。说它「只读图里的文字」的报道已经过时，不要据此推理。
- 2×2 和 3×3 的总图上的数字和图表都读对了；一张表被说成了折线图（实测 2026-10-29）。
- 按上传顺序对照图表，不看文件名：48 张编号文件里，两次把素材画面说成别的图的图表（实测 2026-10-29）。所以每张图上要印编号。
- 一条消息最多 50 个文件（IT之家 2026-04-08 报道，非官方）；不收 zip。
- 带 48 张图和完整提示词的第一轮：附文件 1 秒，回答 42–165 秒（实测 2026-10-29）。

## 限流

- 限的是账号，不是对话：两个对话在几秒内分别于第 6 条和第 2 条消息被拒；新对话的 45 个上传全被拒（实测 2026-10-30）。
- 四个任务 15 分钟里发了 21 条消息被拒，14 分钟后仍被拒；20 分钟 15 条没被拒（实测 2026-10-30）。官方没有公布限额。
- 信号：一个 `hint` 事件，`finish_reason` 为 `rate_limit_reached`，页面上什么都不显示；上传返回 `rate limit reached`，页面显示为 Server busy。
- 「Too many concurrent requests」也是一种繁忙提示。

## 页面的表现

- 回答写完的标志：发送按钮不再显示停止方块。回答的最后几行在按钮恢复后片刻才到页面上（实测 2026-10-30），所以要隔一会儿再读一次。
- 页面不保留所有早先的回答：到第三轮时第一轮的回答块已经不在了，按回答块的数量判断新回答会一直等下去（实测 2026-10-30）。
- 一次发送后，回答还没有思考和文字、附的图也没读时，页面显示「正在分析图片」；有一次 8 分钟都这样，服务器上没有这次发送的消息（实测 2026-10-30）。重发后几秒内就开始思考。
- 上传失败的图，卡片本身就是页面的重试；文件已经在服务器上时，Server busy 来自查询它的状态，点重试只是再查一次。
- 窗口被遮住、最小化或在屏幕外时，Windows 的遮挡检测让 Chromium 把它当成隐藏，页面不绘制（每秒 0 帧），流式的回答到不了页面元素里。关掉 `CalculateNativeWinOcclusion` 并让窗口不节流后，遮住、最小化、在屏幕外都正常绘制（约每秒 110 帧）；两样都要，只不节流仍不绘制（实测 2026-10-30）。
- 每条消息都会让模型重读整个对话：89,000 token 六轮后涨到 160,000（实测 2026-10-30）。

## 怎样查页面

- 用脚本读页面的 DOM、数据和请求，不看截图：截图只有可见的部分，曾导致改错（2026-10-30）。脚本打印的东西要过滤，请求和响应里带登录令牌。
- 随便看看：另开一个 Electron 探针，用临时的 userData，放进 `Partitions/deepseek` 和 `Local State` 的副本，窗口放在屏幕外，拦掉 `/api/v0/chat/completion`，不从用户的账号发出任何东西。
- 查运行中的任务卡在哪：`node -e "process._debugProcess(<主进程 PID>)"` 在 127.0.0.1:9229 打开主进程的调试器，在里面用 `process.mainModule.require('electron')` 和 `webContents.executeJavaScript` 查，查完关掉调试器。
- 页面脚本（fe-static.deepseek.com/chat/static/main.*.js，一行约 1.6 MB）可以下载下来按字符串搜条件。
- 服务器上的对话历史可以用脚本取回，用来核对回答是否完整、每一轮改了多少。
